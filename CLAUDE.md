# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`eduparents` is a pixel-mockup of a parent-facing school app (Vietnamese UI, "EDU Parent"), rendered as a single Next.js page inside a fake iPhone frame. There is no backend, no router and no real data. The app lives in `web/`; a sibling project, **eduteachers**, is not in this repo and is only referenced in code comments as the pattern source.

The repo root also holds the original vanilla prototype (`index.html`, `scripts/app.js`, `styles/main.css`). It is the reference `web/` is being ported from. Screens not yet rebuilt in `web/` still exist only there.

`reference/` is the spec source: screenshots plus `prd.md`, `screens.md` and `flows.md`. Read them before building a screen that doesn't exist in `web/` yet. They are written in Vietnamese and describe only what appears in the screenshots.

## Commands

Run everything from `web/`. The lockfile is `pnpm-lock.yaml`. pnpm is not installed globally on every machine, so `npx pnpm@9 …` works. `.claude/launch.json` starts the dev server with `npm run dev` instead.

```bash
cd web
pnpm install --frozen-lockfile
pnpm dev                 # next dev -p 3100  → http://localhost:3100
pnpm build               # next build
npx tsc --noEmit         # the real type check
```

- `next.config.mjs` sets `typescript.ignoreBuildErrors: true`, so **`next build` does not type-check**. Run `npx tsc --noEmit` yourself.
- `pnpm lint` is broken: the script is `eslint .` but ESLint is not a dependency.
- There is no test runner and there are no tests.
- `web/.claude/settings.json` is a second, nested settings file, separate from the repo-root `.claude/settings.json`. Both deny `git commit` and `git push` for Claude.

## Architecture

**Navigation** is a single `useState<Screen>` switch in `web/app/page.tsx`, with no router library. The page also draws the phone chrome (`.device-frame`, status bar, `.screen-root`, `#overlay-root`).
- The app opens on the **ECO Me home** (`eco-me/eco-home-screen.tsx`): promo banner with greeting/search/bell, wallet card, 7 service tiles plus "Xem thêm" (`eco-services` = "Danh sách dịch vụ", 19 education services in the order of the real app), the student list and a bottom tab bar. There is no ECO School tile and no ECO Phụ huynh home any more (EDU-1742, 1531): tapping a student card opens that student's Trang Học sinh. The service catalogue is `eco-me/services.ts` (icon key + gradient `tint`, drawn by `eco-me/service-icon.tsx` with lucide); only services with an `intent` are interactive, the rest are muted placeholders (none today). Học bạ số (`digital-report/`, intent `digitalreport`) opens a screen with only the empty state "Chưa có thông tin học bạ số", since its PRD page (PH-06) is empty. Nạp tiền and Chuyển tiền open the wallet flows (`topup-wallet/`, `transfer/`); Rút tiền, Mã thanh toán, search, the banner CTA and the bottom tabs are inert; the bell opens **Thông báo** (`notifications/`, data in `MOCK_NOTIFICATIONS`, tapping an item marks it read and deep-links via its `target`).
- Launching a student-scoped service goes through `shared/use-service-launcher.tsx` (`useServiceLauncher`, `eligibleStudents`): 2+ eligible students → picker sheet, exactly 1 → straight in. Use it for any new service entry point. The same list drives the in-screen switcher: every service screen computes `eligibleStudents(intent)` and shows the header's swap icon (and its picker) only when more than one student qualifies (`canSwitch`); with a single student, as for Hóa đơn, the bar has no icon.
- **Student header (updated 2026-11-25, EDU-1478 / PRD pageId 107852819 BR-08):** every feature screen uses `shared/header.tsx` `StudentHeader`, which renders `StudentBar` in its flat form: avatar, name, lớp and a swap icon; the whole bar is the tap target. No mã học sinh or trường there (Hồ sơ học sinh, the student picker sheet and the payment / invoice detail cards still show them). Do not hand-roll a header per screen. Older notes that say "Đổi" button mean this icon. Every screen receives one `ServiceNav` handler, `onOpenService(intent, studentId)`; `page.tsx` maps the intent to a screen through `INTENT_SCREEN`.
- `activeStudentId` is shared by every screen after Home.
- `returnScreen` stands in for the vanilla app's navigation stack (`App.back()`). Every service screen (Fee, Topup, Báo vắng, Bài tập, Kết quả học tập, Phiếu bé ngoan, Hóa đơn) can be entered from ECO Me home, the service list, the Học sinh screen, Chi tiết thẻ (Nạp điểm) or Hồ sơ học sinh (Gợi ý cho ba mẹ), and its back button returns to whichever it came from. Link student and Hướng dẫn use it too (Hướng dẫn opens from the "?" icon of Học sinh and Chi tiết thẻ). Học sinh has its own `studentOrigin`, because features opened from it overwrite `returnScreen` with `'student'`.
- When adding a feature screen: add it to the `Screen` union and `INTENT_SCREEN` in `page.tsx`, add the intent to `ServiceIntent` (and `eligibleStudents` if gated), give it an `intent` in `eco-me/services.ts`, and add it to `PARENT_SERVICES` in `shared/parent-services.ts`: that one catalogue feeds the Học sinh page (`shared/paged-icon-grid.tsx`, swipeable, 8 icons per page; Học sinh lists only the services `eligibleStudents` allows for that student).
- Deep links and shortcuts: `medicineOrderId`, `chatThreadId` and `absenceOnCreate` in `page.tsx` open Dặn thuốc on an order, Trao đổi on a conversation, Báo vắng on its create form. `subReturn` makes back return to the feature that opened a shortcut (Điểm danh → Báo vắng, Trao đổi → đơn) without overwriting `returnScreen`.

**Features** are self-contained folders under `web/components/parents/<feature>/`. Each has an `index.tsx` (`XxxApp`) that owns the feature's inner screen state and renders sub-screens such as `fee-lookup-screen.tsx` or `homework-submit-screen.tsx`. Many `index.tsx` files carry a comment naming the matching function in `scripts/app.js` (for example `App.startFee()`). Read that function when behaviour is unclear.

**Data** comes from `web/lib/mock-data.ts`, the single source of truth for types and mock data. It deliberately mirrors `STUDENTS` in `scripts/app.js`. Screens read from `MOCK_STUDENTS` and mutate it in place, so state persists until a page reload. Only 3 students exist, and feature gating depends on which one is selected:
- `vy`: mầm non, healthy z-score, `supportsTopUp`, no linked invoice.
- `khoa`: phổ thông, elevated z-score, has invoices, homework, absences and results.
- `lam`: mầm non, underweight z-score.

Gating helpers and flags are `isMamNonStudent` (checks whether `school` contains "Mầm non"), `supportsTopUp`, `hasLinkedInvoice` and `results: null`. Phiếu bé ngoan and Nhật ký chăm sóc are Mầm non only, and Nạp điểm is only for `supportsTopUp` students. Test any gated change against all three students.

**Overlays**: bottom sheets and dialogs must render through `shared/overlay-portal.tsx` (`OverlayPortal`). It portals into `#overlay-root`, a sibling of the scrollable `.screen-root`, and locks body scroll. An inline `.sheet` is `position:absolute` against `.screen-root`, so it scrolls away with the page. Use the existing `.scrim` / `.sheet` classes.

**Styling** is hand-written plain CSS in `web/app/globals.css` on top of the **ECO Design System** ("ECO Me DS"). Three files load in this order from `layout.tsx`: `ds-tokens.css` (every DS token as a CSS variable: `--text-*`, `--bg-*`, `--border-*`, `--space-*`, `--radius-4/8/12/20`, `--text-body-xs/s/m/l`, plus the SF Pro `@font-face` from `public/fonts/*.woff2`; the font stack is `-apple-system, BlinkMacSystemFont, 'SF Pro', 'Segoe UI', Roboto, …`: Apple devices use the system SF (same look as the reference deployment at edu-parents.vercel.app, whose SF Pro files never load), other platforms get the SF Pro webfont. The static SF Pro Text webfont renders about 4% wider than the system font, which looked too big), `eco-ds-bundle.css` (the DS component stylesheet, `.eco-*` classes; it is loaded but the app's screens do not use the DS React bundle) and `globals.css`. It does `@import 'tailwindcss'` and has Tailwind/shadcn deps, but screens do not use utility classes. The legacy `--c-*` names at the top of `globals.css` are aliases that now point at DS tokens (`--c-gray-150` = `--border-soft`, `--c-yellow` = `--eco-yellow`, `--c-navy` = `--text-label`, ...), so old rules render in DS colours; the vanilla app (`styles/main.css`) is no longer kept in sync and stays monochrome. The last block of `globals.css` ("ECO Design System skin") re-skins the shared classes (`.topbar`, `.btn`, `.tab-pill`, `.segmented`, `.badge`, `.sheet`, `.dialog-card`, `.field`, `.search-box`, the icon grids) to the DS look; add DS-wide changes there. Rules: yellow `--eco-yellow` is the primary action (`.btn-primary`, DS Button `brand`), blue `--text-link` is links and selection, `--brand-yellow-strong` is the selected tab pill; text uses only 12/14/16/18 px (24/32 for display numbers) and weights 400/500/700 (never 600 or 800); radii use `--radius-4/8/12/20`, not the DS `--radius-sm/md/lg`. Do not name a new app class `.eco-<name>` if the DS already has it (the app's own were renamed `.eco-me-avatar` / `.eco-me-greeting` for that reason). Service icons are the DS service-tile images in `public/ds/services/*.webp` (map in `shared/ds-service-icon.ts`; services without one keep a gradient glyph tile) and the wallet quick actions use `public/ds/icons/*.svg`, all exported from the DS bundle. Icons elsewhere are still lucide, not DS Hugeicons. The donut colours live in `SEGMENT_COLORS` in `bill-overview-screen.tsx`.

**Hóa đơn** (`components/parents/hoa-don/`) has no vanilla counterpart. It was built from design screenshots: list (entry screen), then Thông tin hóa đơn, then Xác nhận giao dịch, then Kết quả giao dịch (`bill-result-screen.tsx`, from a screenshot: "Trang chủ" calls `onGoHome`, "Giao dịch mới" returns to the Chưa thanh toán tab). The overview's "Phân bổ danh mục" is the shared `CategoryDonut` in `hoa-don/bill-category-donut.tsx`: a non-interactive ring with a % chip per slice (no name) joined by dotted leader lines, then one legend row per category (colour, name, amount; no %); with 5 or fewer categories all are shown, with more the 4 largest stay and the rest fold into "Còn lại", whose legend row opens a bottom sheet listing them. School-year helpers live in `hoa-don/bill-year.ts`. Tổng quan is derived entirely from `student.bills` at render time. The list has a **school-year filter** ("Năm học yyyy - yyyy ⌄" row with a notebook icon, `bill-year-row.tsx`, + bottom sheet; the overview has the same row and sheet (`YearFilter`), so the year can be changed there and the overview reloads for it, `HoaDonApp` state `year`, default = the school year of today, Aug→Jul; options from `availableYears`) under the student card: both tabs, the pay-flow select screen and the overview all load that year (`billsInYear`, `summarizeYear(student, now, year)`), and the overview's month chart ends at today for the current year and at July for a past one (`yearAnchor`). The overview's summary, donut and counts are scoped to the selected year; the total amount and the donut count paid items only, and "Số hóa đơn" counts bills with at least one paid item (fully or partly paid). `summarizeYear` still returns `unpaidCount` (BR-05: no paid item and at least one item still to pay) but no screen shows it. Donut categories are inferred from item names (`Học phí…`, `Tiền ăn…`, else the name itself). The month chart lists every month of the selected school year up to today (July for a past year), months without payments included (a 0 bar; tapping it says there is nothing paid); 5 are visible at a time and it scrolls sideways (`VISIBLE_MONTHS`), opening on the latest months; a row above it shows the visible range ("Tháng mm/yyyy - Tháng mm/yyyy") with < > buttons that move one month within the school year (never past today), and the scroll snaps to whole month columns (`scroll-snap`), so it always rests on 5 full columns, with a fixed amount axis on the left (0, half, top; the top is a round number from `niceCeil`) beside the scrolling bars, placed by billing period (`Bill.year`/`month`, not payment date). No month is preselected; tapping a bar lists that month's paid items, grouped into collapsible bills when the month has more than one. The Aug–Oct 2026 mock bills (5 in school year 2026-27: 3 fully paid, one of them without VAT, 1 partly paid, 1 unpaid) exist so it has data when opened in Oct 2026. "Xem hóa đơn ›" (shown only on fully paid bills with `hasVat`) opens `bill-invoice-pdf-screen.tsx`, an iframe on the static sample `web/public/invoices/<bill.id>.pdf` with back and download in the top bar; each `hasVat` bill needs its own PDF there. The warning row "Hóa đơn chưa được thanh toán xong" + "Thanh toán ngay" button on a partly paid bill (Đã thanh toán tab) opens the normal select screen (Thông tin hóa đơn) with every open item unchecked, same as the "Chưa thanh toán" tab's CTA. It uses its own `Student.bills` model (per-item `paid` flags), separate from `invoices`, which only drives Đóng học phí. A bill with some items paid appears in both tabs. Only `khoa` has bills, so the Home picker lists only students with `bills.length > 0`, and Home skips the picker when only one student qualifies. On Kết quả giao dịch the promo cards and "Chia sẻ" are inert. **DS look (2026-10-20):** the list, select, confirm and result screens use the DS classes directly (`eco-segment` tabs, `eco-billgrp` BillGroup for Chưa thanh toán, `eco-paidbill` PaidBillCard for Đã thanh toán, `eco-paycheck`, `eco-txn` TransactionSummary, `eco-paylist` / `eco-payopt`, `eco-actionfooter` / `eco-totalfoot`); shared bits are in `hoa-don/bill-ds.tsx` and the `.bill-ds*` rules at the end of `globals.css`. Paid amounts keep their leading minus (PRD).

**Gợi ý nhập liệu, nháp và chỉ dẫn lần đầu** (Jira EDU-2095, EDU-2118, EDU-2106; PRDs published 2026-11-27, aligned with them the same day: Báo vắng pageId 107853509, Trao đổi 107853456, Hướng dẫn lần đầu 107853455; UI images `…/.claude/worktrees/confluence-reading-methods-5d686b/prd-drafts/*-v2.png`):
